# XKeen Installer

Графический мастер установки XKeen, Mihomo/Xray, router-watchdog и XKeen UI PWA на подготовленный Keenetic.

## Подготовка роутера

Для новой установки подготовьте EXT4-раздел, установите компоненты OPKG, SSH и SMB в KeeneticOS и разрешите учётной записи доступ к существующему SMB-ресурсу корня раздела. Выберите в мастере новую установку и подключитесь к SSH администратора KeeneticOS (обычно `admin:22`). Мастер определяет точную модель и архитектуру, предлагает подходящие EXT4-разделы, использует встроенный проверенный offline-архив и переносит его после проверки и вашего подтверждения конкретного плана. При нескольких разделах цель выбираете вы. Другой OPKG-диск, существующее дерево Entware, пользовательский initrc, неоднозначный SMB-ресурс или чужой установочный архив блокируют bootstrap.

План показывает UUID, архив, SHA256 и точные изменения OPKG. На проверенном пустом разделе он явно задаёт временный Initrc `/opt/etc/init.d`, чтобы KeeneticOS запустил `doinstall` из архива. Установщик из локального набора затем задаёт конечный `/opt/etc/init.d/rc.unslung` и сохраняет настройки; пользовательский initrc блокирует bootstrap. Для уже выбранного того же пустого раздела он включает снятие привязки OPKG и повторное назначение этого UUID. Архив проверяется по закреплённым разработчиком размеру и SHA256, структуре tar и ELF-архитектуре `bin/opkg`; после передачи проверяется обратным чтением. Архив включает закреплённый локальный репозиторий базовых пакетов и зависимостей; opkg не загружает их из сети. Происхождение исходных архивов, локальная правка locales без HTTP-fallback и итоговые хеши описаны в [entware-byte-pins.md](docs/entware-byte-pins.md). При изменении байтов установка блокируется.

Перед подготовкой плана задайте отдельный новый пароль root Entware и повторите его: минимум 16 символов, максимум 1024 байта UTF-8, без NUL и переводов строк. Пароль KeeneticOS остаётся прежним. На роутер передаётся только хеш; подписанный SMB не гарантирует его шифрование, поэтому используйте длинный уникальный пароль. SSH Entware открывается только после установки пароля и генерации новых ключей сервера.

После запуска OPKG проверьте в KeeneticOS Initrc `/opt/etc/init.d/rc.unslung` и подключитесь к SSH Entware (обычно `root:222`) с заданным новым паролем (введите его повторно в поле подключения). Новый SSH-ключ требует отдельного подтверждения. В текущей bootstrap-сессии мастер также проверяет конечный firmware Initrc и исполняемый `rc.unslung`. Только успешный inspector с `opkg list-installed` позволяет перейти к установке XKeen; переданный архив не означает работоспособный Entware. Для существующего Entware сразу используйте режим существующей установки. Форматирование, установка компонентов KeeneticOS, настройка SMB-доступа, DNS и политики выполняются вручную; мастер не перезагружает роутер.

Последовательность работы: подготовка → подключение → проверка → ядра → компоненты → конфигурация → просмотр и подтверждение плана → установка → проверка результата. Конфликты конфигурации требуют ручного согласования. До записи создаётся проверяемая закрытая резервная копия. Отмена сохраняет выполненные изменения; повтор требует новой проверки и подтверждения нового плана.

Пароли и подписки не сохраняются в browser storage или отчётах. Первый ключ SSH подтверждается отдельно и хранится в памяти до закрытия приложения; неожиданная замена блокируется. Ключ локального CA остаётся в закрытом хранилище компьютера. Новые CA действуют один год, серверные сертификаты — 90 дней; критические Name Constraints ограничивают выдачу адресом роутера для проверяющих, которые применяют эти ограничения. Уже выпущенные CA и сертификаты автоматически не заменяются. Проверки Go не гарантируют одинаковое применение ограничений всеми ОС и браузерами. Установка доверия CA требует отдельного подтверждения; на других устройствах доверие настраивается вручную.

Для существующего Entware перед установкой проверьте `/opt/etc/opkg.conf` и `/opt/etc/opkg/*.conf`: HTTP-источники и `option no_check_certificate` блокируются. Сохраните резервную копию этих файлов, переведите источники на HTTPS и восстановите проверку сертификатов, если она была отключена. Мастер эти настройки не переписывает. Незавершённые пакетные операции и смена версии зависимости с непроверенными старыми hooks также блокируются; автоматического ремонта пакетов нет. Если присутствует `/opt/lib/functions.sh` с дополнительными opkg hooks, требуется отдельная проверка: неизвестные callbacks автоматически не запускаются.

## Сборка

Зафиксированы Wails 2.17.1, Go 1.26.11 и Node.js 26.5.0 с npm. Нужны системные зависимости [Wails v2](https://v2.wails.io/docs/gettingstarted/installation/). WebView берётся из системы:

| Цель | Среда сборки и запуска | Результат |
| --- | --- | --- |
| Windows amd64 | Windows 10/11, установленный WebView2 Runtime | `xkeen-installer.exe` в ZIP |
| macOS amd64/arm64 | macOS 12+, Xcode Command Line Tools для сборки, системный WKWebView | `xkeen-installer.app` в ZIP |
| Linux amd64 | Ubuntu 24.04; GTK 3 и WebKitGTK 4.1, для сборки также gcc/pkg-config и development packages | `xkeen-installer` в tar.gz |

Минимум macOS 12 учитывает [требования Go 1.26](https://go.dev/wiki/MinimumRequirements); работа на старых версиях macOS не проверена. Linux-архив зависит от системных библиотек Ubuntu 24.04 и не является универсальным пакетом для всех дистрибутивов.

Из корня проекта:

```sh
cd frontend
npm ci
npm run typecheck
npm test
npm run build
cd ..
go test ./...
go vet ./...
go run github.com/wailsapp/wails/v2/cmd/wails@v2.17.1 build
```

На Linux установите `build-essential pkg-config libgtk-3-dev libwebkit2gtk-4.1-dev`; добавляйте `-tags webkit2_41` к Go test/vet и Wails build. На Windows используйте `build -platform windows/amd64 -webview2 error`: приложение требует установленный WebView2 и не загружает его автоматически. На macOS для минимума 12 задайте `CGO_CFLAGS=-mmacosx-version-min=12.0` и `CGO_LDFLAGS=-mmacosx-version-min=12.0` перед сборкой.

На macOS результат находится в `build/bin/xkeen-installer.app`. Режим разработки: `go run github.com/wailsapp/wails/v2/cmd/wails@v2.17.1 dev`.

## Что проверено

На компьютере: тесты Go, vet, frontend typecheck/тесты/production build и нативная сборка macOS arm64. Сценарии установки проверяются через fixtures, а SSH/SFTP и HTTPS — локальными тестовыми серверами. Команды, соответствие сценариям и ограничения перечислены в [docs/testing.md](docs/testing.md).

GitHub Actions проверяет pull request в `main` и собирает четыре установщика: Windows x64 (`.exe`, NSIS), Linux x64 (`.deb`, Ubuntu 24.04), macOS Intel и Apple Silicon (`.dmg`). Файлы доступны в artifacts запуска.

После мержа в `main` (а также прямого push в `main`) workflow выбирает следующую patch-версию, выполняет тесты и все четыре сборки, затем публикует аннотированный тег и GitHub Release с установщиками и `SHA256SUMS`. Первый выпуск — `v0.1.0`, следующий — `v0.1.1`. Версия в метаданных приложений выставляется при сборке. При ошибке любой сборки релиз не публикуется. Повторный запуск коммита с существующим тегом использует прежнюю версию. Доступен ручной запуск workflow из `main`.

Скачать установщики: [GitHub Releases](https://github.com/Arap919/Xkeen-installer/releases/latest). Для установки Linux-пакета: `sudo apt install ./xkeen-installer-*-linux-amd64.deb`. На macOS откройте DMG и перенесите приложение в Applications. На Windows запустите setup EXE; нужен WebView2 Runtime.

На реальном роутере: установка, сетевые политики, запуск ядер, watchdog, HTTPS/PWA и повтор после обрыва не проверены. Системное доверие CA также не устанавливалось. Fixtures не подтверждают работу пакетов и служб на устройстве.

Установщики выпускаются без подписи сертификатом издателя и без Apple notarization. Wails может выполнять локальную ad hoc подпись macOS. Windows и macOS могут предупреждать о неизвестном издателе; подпись для распространения требует отдельных сертификатов.

Базовый Xray-шаблон создан по пользовательскому Mihomo-конфигу: [маршруты, подключение прокси и отличия](docs/xray-base.md).

Полный пользовательский Mihomo-конфиг встроен в сборку: порты, DNS Fake-IP, группы и правила. На шаге конфигурации можно указать до 10 HTTPS-подписок для каждого выбранного ядра. Mihomo использует провайдеры VPNProvider, VPNProvider1–VPNProvider9; группы Proxy и BENCHMARK используют все заданные провайдеры. В рабочем экземпляре API и benchmark ограничены loopback, создаётся случайный API secret; watchdog использует Proxy/BENCHMARK. Существующие конфигурации не заменяются.

Локальный файл и подписки выбираются по отдельности. Для Xray поддерживаются JSON-объект с outbounds или массив таких объектов: мастер импортирует только прокси-подключения, сохраняя базовые DNS и маршруты, и выбирает первый подходящий узел. URL скрыты в интерфейсе и очищаются при запуске, завершении и закрытии сессии. Для новых управляемых конфигураций Xray подписки обновляются каждые 12 часов; перед заменой выполняются проверка конфигурации и контроль хеша, поэтому ручные изменения не перезаписываются. Cron устанавливается и проверяется автоматически по подтверждённому плану; существующие задания сохраняются, неоднозначная или конфликтующая служба блокирует установку. Геобазы Xray берутся из закреплённого ZIP ядра; пользовательские базы сохраняются.
### Если новая установка Entware прервалась

Не выбирайте существующий Entware, пока его inspector не подтвердил готовность.
Повторное копирование поверх частичного дерева мастер блокирует. Сохраните доступ
администратора KeeneticOS и SMB к выбранному разделу: они не зависят от нового
пароля Entware. Стандартный пароль для восстановления не включается.

Безопасный путь повторной установки: через KeeneticOS отключите использование
незавершённого OPKG-раздела, сохраните его целиком как резервную копию и подготовьте
отдельный чистый EXT4-раздел штатными средствами. Затем снова выберите новую
установку, проверьте UUID/SMB-ресурс и задайте новый пароль. Исходный раздел мастер
не удаляет и не форматирует. Если отдельного раздела нет, сначала требуется
ручное решение о сохранении данных и очистке нужного раздела; автоматического
удаления частичного Entware нет.

Пропавшая или устаревшая готовность SSH (в том числе после ручной замены passwd
или host keys) блокирует запуск службы. Не создавайте файл ready вручную для
обхода проверки; сначала требуется отдельная проверка состояния через KeeneticOS
и резервную копию накопителя. Существующие установки, созданные вне этого
bootstrap, своих паролей и init-скриптов не меняют.

## Проверка происхождения установщика

Новый release-job создаёт GitHub/Sigstore attestations для четырёх установщиков
и `SHA256SUMS`. В них закреплены хеши финальных файлов и сведения о workflow,
исходном коммите и окружении сборки. Проверка attestation обязательна до
публикации релиза; ошибка останавливает выпуск. Права OIDC и записи attestations
выданы только release-job при push или ручном запуске из `main`. PR и сборки
других веток таких прав не получают. Долгоживущие ключи подписи не хранятся.

Это начнёт работать с первым релизом, выпущенным обновлённым workflow из `main`.
Старый `v0.1.0` задним числом не аттестуется. Наличие workflow artifact
provenance attestations для его бинарников не подтверждено.

Установите GitHub CLI и скачайте установщик из официального релиза.
Подставьте его имя вместо примера с VERSION и ожидаемый полный SHA исходного
коммита вместо COMMIT_SHA. Коммит следует сверять с доверенной версией исходников
релиза. Команда подходит для Bash и PowerShell:

```text
gh attestation verify ./xkeen-installer-VERSION-windows-amd64-setup.exe --repo Arap919/Xkeen-installer --cert-identity https://github.com/Arap919/Xkeen-installer/.github/workflows/build.yml@refs/heads/main --source-digest COMMIT_SHA --deny-self-hosted-runners
```

Для Linux/macOS укажите имя соответствующего DEB/DMG. Для проверки манифеста
выполните ту же команду с `./SHA256SUMS`. Ожидается успешный код завершения:
attestation из другой ветки, другого workflow или для другого содержимого
не должна приниматься. Простое совпадение с неаутентифицированным SHA256SUMS
этой проверки не заменяет.

Attestation подтверждает происхождение из указанного GitHub workflow, а не
безопасность самого исходного кода. Она не заменяет Windows Authenticode,
Apple Developer ID и notarization: предупреждения ОС о неизвестном издателе
могут сохраняться. Платные сертификаты в этом этапе не используются.

Техническая справка: [GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)
и [параметры gh attestation verify](https://cli.github.com/manual/gh_attestation_verify).
